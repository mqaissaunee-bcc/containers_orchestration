2The OpenShift family

Week 8 introduced OpenShift as a Kubernetes distribution. It comes in several forms, all built from the same code:

  • OKD is the free community distribution, the upstream project OpenShift is built from.
  • Red Hat OpenShift Container Platform is the supported product you install on your own hardware, virtual machines or cloud accounts. Related editions bundle more (OpenShift Platform Plus) or less (OpenShift Kubernetes Engine).
  • Managed OpenShift runs the platform for you: Red Hat OpenShift Service on AWS (ROSA), Azure Red Hat OpenShift (ARO) and OpenShift Dedicated.
  • The Developer Sandbox is a free, shared, time-limited managed cluster for learning.

This course follows OpenShift 4.14. Commands, resource types and concepts are the same across all of these; what differs is who installs, upgrades and pays for the cluster, and how much access you get. On the Sandbox you're an ordinary developer; on a classroom cluster your instructor may give you administrator rights.

3Cluster architecture

A production OpenShift cluster has two kinds of machines:

  • Control plane nodes, normally exactly three. They run the API server, the etcd database, the scheduler and the controller managers. Three nodes let etcd keep a majority, a quorum, if one fails. Your applications don't run here.
  • Compute nodes, also called workers, which run your pods. Clusters add or remove them as demand changes. Some clusters also dedicate infrastructure nodes to platform services such as the router, the internal registry and monitoring.

Every node runs Red Hat Enterprise Linux CoreOS (RHCOS), a minimal, mostly read-only RHEL variant built for running containers. You don't log in and install packages on it; the cluster itself manages each node's configuration and upgrades. On each node:

  • kubelet receives pod assignments and keeps those pods running.
  • CRI-O pulls images and runs containers, using the same libraries as Podman.
  • OVN-Kubernetes gives every pod an IP address and connects pods across nodes.

A small single-node OpenShift (SNO) variant puts everything on one machine for edge locations and labs. It works the same way but has no redundancy.

Why so much automation?

A cluster may have hundreds of nodes. Treating them as identical, replaceable machines managed by the cluster, rather than as individual servers someone logs into, is what lets a small team run it.

4Operators run the cluster

In Week 8 you saw controllers reconcile deployments: observe, compare, act. An operator applies that same loop to a whole piece of software. It packages the operational knowledge a skilled administrator would have, how to install it, configure it, upgrade it, back it up and recover it, as code that runs inside the cluster.

OpenShift is itself managed by operators:

  • The Cluster Version Operator (CVO) owns the cluster's version. It installs and upgrades about thirty cluster operators, one per platform component: the API server, the router (ingress), DNS, the internal image registry, the web console, monitoring, networking and more.
  • Each cluster operator reports three conditions: Available (working), Progressing (changing, for example during an upgrade) and Degraded (something is wrong). oc get clusteroperators is the first health check an administrator runs.
  • Operator Lifecycle Manager (OLM) installs optional add-on operators from OperatorHub, for databases, storage, service meshes, GitOps and pipelines, among others.
$ oc get clusterversion
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE   STATUS
version   4.14.12   True        False         12d     Cluster version is 4.14.12
$ oc get clusteroperators
NAME              VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE
authentication    4.14.12   True        False         False      12d
console           4.14.12   True        False         False      12d
…

Both commands need cluster administrator rights. On the Developer Sandbox you'll get a "forbidden" error, which is correct behavior.

6The web console

Everything oc can do, the web console can show. Find its address with oc whoami --show-console. In OpenShift 4.14, a switcher at the top of the left-hand menu chooses between two perspectives:

  • Administrator organizes the cluster by resource type: Home (overview and cluster health), Operators (OperatorHub and installed operators), Workloads (pods, deployments), Networking (services, routes), Storage, Builds, Observe (metrics, alerts, events), Compute (nodes) and User Management.
  • Developer organizes it around applications: +Add (deploy from an image, Git, YAML or a catalog), Topology (a live map of your app's components), Observe and Search.

Useful console features to know:

  • YAML views. Every resource page has a YAML tab where you can read, edit and save the full resource definition.
  • Copy login command, under your user name in the top right, gives you an oc login command with a token.
  • Command Line Tools, under the help menu, downloads oc for your operating system.
  • Web terminal, an optional operator that opens a shell with oc already logged in, right in the browser.
Exam and lab habit

The console is great for exploring and confirming. Do the work with oc, though: commands are faster to repeat, easy to check, and the only option in scripts. Many graded tasks are much quicker from the command line.

7Users, projects and permissions

Authentication: who are you?

OpenShift's built-in OAuth server checks your identity against one or more identity providers that an administrator configures: a simple htpasswd file in classrooms, or LDAP, Active Directory, GitHub or an OpenID Connect service in companies. After you log in, you get a token, and every oc command sends it with each API request. A new cluster also has a temporary kubeadmin user that administrators replace with real accounts.

Authorization: what may you do?

Role-based access control (RBAC) grants permissions through roles. A role lists allowed actions (verbs such as get, list, create, delete) on resource types. A role binding gives a role to a user or group, in one project or across the whole cluster. The default roles you'll meet most often:

Common default roles
RoleAllows
viewRead most resources in a project, but not secrets.
editCreate, change and delete most resources in a project, but not change its permissions.
adminEverything in the project, including granting roles to others. You get this on projects you create.
cluster-adminEverything, everywhere, including nodes and cluster settings.

A project is a Kubernetes namespace plus OpenShift extras: a display name, description, and the default permissions above. Projects separate teams, environments and applications, and they're the scope for quotas you'll meet later.

Not sure whether you're allowed to do something? Ask the API instead of guessing:

$ oc auth can-i create deployments
yes
$ oc auth can-i get nodes
no

    9Beyond Red Hat

    The same architecture elsewhere

    • Same core everywhere. The API server, etcd, scheduler, controller manager and kubelet are upstream Kubernetes components. On any cluster, a request takes the same path you just stepped through.
    • Hidden control planes. Managed services such as Amazon EKS, Google GKE and Azure AKS run the control plane for you and don't show it at all. You see only your worker nodes, and you pay per cluster for the control plane.
    • Container-focused operating systems. RHCOS has counterparts: Fedora CoreOS (its community sibling), Flatcar Container Linux, Bottlerocket on AWS and Talos Linux.
    • Operators beyond OpenShift. The operator pattern and Operator Lifecycle Manager work on any Kubernetes cluster; OperatorHub.io lists community operators. Many vendors ship their software as Helm charts instead.
    • Other consoles. Upstream Kubernetes has an optional Dashboard, and popular desktop and terminal tools include Lens, Headlamp and k9s.
    • RBAC is standard Kubernetes. Roles, cluster roles, bindings and kubectl auth can-i work the same way on every cluster. Authentication differs most: managed services usually tie into their cloud's identity system.
