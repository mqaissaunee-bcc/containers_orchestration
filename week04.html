1Goals

By the end of this week you should be able to:

  • Write a Containerfile and build it with podman build.
  • Choose the right instruction for each job, including COPY versus ADD and ARG versus ENV.
  • Order instructions so the build cache saves you time.
  • Predict the command a container runs from its ENTRYPOINT, CMD and podman run arguments.
  • Build images that run as a non-root user and work under OpenShift's random user IDs.
  • Reduce image size with careful RUN instructions, minimal base images and multi-stage builds.

2What a Containerfile is

A Containerfile is a plain text file of instructions, read top to bottom, that turns a base image into a new image. It uses exactly the same format as a Dockerfile, and Podman accepts either name. Here is a small but complete one:

# Containerfile
FROM registry.access.redhat.com/ubi9/ubi-minimal:9.4
LABEL description="NETW 112 hello page"
RUN microdnf install -y httpd && microdnf clean all
COPY index.html /var/www/html/
EXPOSE 80
CMD ["httpd", "-D", "FOREGROUND"]

You build it from the directory that holds it:

$ podman build -t myhello:1.0 .
STEP 1/5: FROM registry.access.redhat.com/ubi9/ubi-minimal:9.4
STEP 2/5: LABEL description="NETW 112 hello page"
--> 5b0c…
STEP 3/5: RUN microdnf install -y httpd && microdnf clean all
…
COMMIT myhello:1.0
Successfully tagged localhost/myhello:1.0

Two details trip people up. The final . is the build context: the directory whose files COPY can see. COPY can never reach outside it. And -t names the result; without a registry in the name, the image lands in localhost/, exactly like podman tag last week. Use -f if the file has a different name or location.

Everything in the context directory is sent to the build. Keep it lean with a .containerignore file that lists what to leave out, such as .git, build output and local secrets.

About that example

It works as root, but it listens on port 80 and runs as root. Sections 6 and 7 fix both problems, and the workbench lets you watch the fixes change the result.

4Layers and the build cache

Each RUN, COPY and ADD adds a filesystem layer; the other instructions only change the image's metadata. Podman remembers every step it has built. On the next build it walks down the Containerfile, and as long as an instruction is unchanged (and, for COPY and ADD, the files it copies are unchanged) it reuses the saved result instead of running it again. You'll see --> Using cache in the output.

The cache breaks at the first step that changed, and every step after that is rebuilt, even if those later lines didn't change. That leads to the most important ordering rule in this chapter: put what changes least at the top. Install packages first; copy your application code last. Then an edit to index.html rebuilds one quick COPY step instead of reinstalling every package.

Layers also explain image size. Files deleted in a later layer still exist in the earlier one, so

RUN dnf install -y httpd
RUN dnf clean all

doesn't shrink anything: the package cache is still stored in the first layer. Clean up in the same RUN that made the mess:

RUN dnf install -y httpd && \
    dnf clean all

5ENTRYPOINT and CMD

Both instructions concern what runs when the container starts, and they combine in ways that are easy to get wrong:

  • With only CMD, it is the whole command. Arguments to podman run replace it completely.
  • With ENTRYPOINT and CMD, ENTRYPOINT is the program and CMD supplies its default arguments. Arguments to podman run replace only the CMD part. Override the entrypoint itself with podman run --entrypoint.

Each instruction also has two forms. The exec form, a JSON array such as ["httpd", "-D", "FOREGROUND"], runs the program directly as PID 1. The shell form, plain text such as httpd -D FOREGROUND, runs it inside /bin/sh -c. With the shell form, the shell is PID 1 and usually doesn't pass SIGTERM along, so podman stop waits the full 10 seconds and then kills your app. A shell-form ENTRYPOINT also ignores CMD and any run arguments entirely.

Predict the process

Choose an ENTRYPOINT, a CMD and the arguments given to podman run. The result shows exactly what runs as PID 1.

6Images that run anywhere

An image that works with podman run on your laptop can still fail in production. The usual reason is that it quietly assumes it runs as root. Build with these habits from the start and the same image will run rootless under Podman and on OpenShift without changes.

  • Install as root, run as someone else. Do your package installs and file setup first, then switch with USER 1001 near the end. A numeric UID is better than a name because a platform can check it is non-zero without looking anything up.
  • Plan for an unknown UID. By default OpenShift ignores your USER and runs the container with a random, high UID that belongs to group 0 (root's group, which grants no special privileges). Make every directory the app writes to owned by group 0 and group-writable: chgrp -R 0 DIR && chmod -R g=u DIR.
  • Listen on a high port. Non-root processes can't bind ports below 1024, so configure the app for a port such as 8080 and EXPOSE that.
  • Log to standard output. Then podman logs and OpenShift's logging see everything.
  • Configure with environment variables and keep secrets out of the image entirely. They'll be supplied at run time, as you'll see with OpenShift secrets in Week 14.
FROM registry.access.redhat.com/ubi9/ubi-minimal:9.4
RUN microdnf install -y httpd && microdnf clean all && \
    sed -i 's/^Listen 80$/Listen 8080/' /etc/httpd/conf/httpd.conf && \
    chgrp -R 0 /var/log/httpd /run/httpd && \
    chmod -R g=u /var/log/httpd /run/httpd
COPY index.html /var/www/html/
EXPOSE 8080
USER 1001
CMD ["httpd", "-D", "FOREGROUND"]
Order matters

If USER 1001 comes before the package install, the build fails: an unprivileged user can't install packages. Switch users after the root-only work is done.

7Keeping images small

Smaller images pull faster, start faster and contain fewer packages that could carry vulnerabilities. Four techniques do most of the work:

  • Start small. ubi-minimal is roughly half the size of ubi; ubi-micro is smaller still.
  • One RUN per logical task, cleaned up in place. Chain related commands with && and remove package caches and temporary files in the same RUN.
  • Install only what you need. Every package is size and attack surface. Skip editors, compilers and debugging tools in production images.
  • Use a multi-stage build when you compile code. The first stage has the compiler; the final stage copies in just the finished program. Nothing from the build stage ends up in the final image unless you copy it.
FROM registry.access.redhat.com/ubi9/go-toolset:1.21 AS build
COPY main.go go.mod ./
RUN go build -o /tmp/hello .

FROM registry.access.redhat.com/ubi9/ubi-micro:9.4
COPY --from=build /tmp/hello /usr/local/bin/hello
USER 1001
EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/hello"]

The Go toolchain image is well over a gigabyte. The final image is the small micro base plus one binary.

    9Beyond Red Hat
    
    
    Building images elsewhere
    
    
    
      
    Dockerfile and Containerfile are the same format. podman build accepts either name, and docker build will build a Containerfile if you pass -f Containerfile. Everything in this chapter applies to both.
    
      
    Docker BuildKit
    
      
    Docker's builder, BuildKit, is the default in current Docker Engine releases. Two of its features are worth knowing, and Podman and Buildah support both:
    
      
      
        
    • Multi-platform builds. docker buildx build --platform linux/amd64,linux/arm64 builds one image for Intel and ARM machines, published as a manifest list. The Podman equivalent is podman build --platform … --manifest NAME.
      • 
        
    • Cache mounts. RUN --mount=type=cache,target=/root/.cache/pip pip install … reuses a download cache between builds without storing it in a layer.
      • 
      
    
      
    Other base images
    
      
      
        
    • Alpine Linux: tiny (a few megabytes), but it uses the musl C library instead of glibc, which occasionally breaks software built for glibc.
      • 
        
    • Debian slim and Ubuntu: familiar package managers, moderate size.
      • 
        
    • Distroless (Google) and Chainguard images: no shell or package manager at all, like UBI micro, designed to minimize attack surface.
      • 
      
    
      
    Building without a Containerfile
    
      
    Cloud Native Buildpacks (the pack tool) and OpenShift's Source-to-Image (S2I) detect your application's language and produce an image straight from source code. You'll see S2I builds on OpenShift later in the course.
    
      
    Linting
    
      
    hadolint is a popular open source Dockerfile linter that checks many of the same rules as this week's workbench review. Add it to your build pipeline.
