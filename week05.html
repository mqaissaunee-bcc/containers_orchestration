Week 5

Keeping data alive

Containers are meant to be thrown away, but your data isn't. This week you store data outside the container with volumes and bind mounts, and learn the two Linux security layers, SELinux and user namespaces, that decide whether a container can actually read and write it.

1Goals

By the end of this week you should be able to:

  • Explain why data written inside a container is lost when the container is removed.
  • Create, use, inspect, back up and remove named volumes.
  • Mount a host directory into a container, read-only or read-write.
  • Choose between the :z and :Z SELinux options and recognize an SELinux denial.
  • Explain how rootless Podman maps container UIDs to host UIDs, and fix ownership with podman unshare or :U.
  • Run a containerized database whose data survives container replacement.

2Why container data disappears

Recall from Week 1 that a container is an image's read-only layers plus one thin writable layer. Everything the container writes, whether log files, uploaded images or database tables, lands in that writable layer. podman rm deletes the layer, and the data goes with it.

That is by design. Replacing containers rather than repairing them only works if the container holds nothing you'd miss. So we split applications into two kinds of content:

  • The application itself (code, libraries, default configuration) belongs in the image, rebuilt whenever it changes.
  • State (database files, uploads, anything users create) belongs outside the container, in storage that outlives any single container.

Podman offers two kinds of outside storage: named volumes, which Podman manages for you, and bind mounts, which expose a directory you choose on the host. The writable layer is also slower than either, because every write goes through the overlay filesystem's copy-on-write machinery.

3Named volumes

A named volume is a storage area that Podman creates, tracks and cleans up. You refer to it by name and never need to know where it lives. The -v option mounts it into the container at a path: volume name:container path.

$ podman volume create web-data
$ podman run -d --name web -p 8080:8080 -v web-data:/var/www/html registry.access.redhat.com/ubi9/httpd-24
$ podman volume ls
DRIVER      VOLUME NAME
local       web-data
$ podman volume inspect --format '{{.Mountpoint}}' web-data
/home/student/.local/share/containers/storage/volumes/web-data/_data

If the volume doesn't exist yet, podman run -v creates it automatically. When an empty volume is first mounted over a path that already has content in the image, Podman copies that content into the volume, so the app still finds its default files.

Named volumes are the right default for application data. Podman handles their SELinux labeling for you, and because they live in your container storage, the ownership puzzles in section 6 rarely come up.

Lifecycle and backup

$ podman volume export web-data -o web-data.tar   # back up
$ podman volume import web-data web-data.tar      # restore into an existing volume
$ podman volume rm web-data                       # fails while a container uses it
$ podman volume prune                             # remove every unused volume
Prune carefully

A volume counts as unused when no container, running or stopped, references it. If you removed a database container last week and planned to reattach its volume later, podman volume prune deletes the data permanently.

4Bind mounts

A bind mount makes an existing host directory, or a single file, appear inside the container. Changes on either side are instantly visible on the other. That makes bind mounts ideal for:

  • Development, where you edit code on the host and the container serves it immediately.
  • Supplying configuration files that you manage on the host.
  • Data that other host tools need to read, such as backups or reports.
$ mkdir site
$ podman run -d --name site -p 8081:8080 -v ./site:/var/www/html:Z registry.access.redhat.com/ubi9/httpd-24
$ podman run --rm -v ./app.conf:/etc/app/app.conf:ro,Z registry.access.redhat.com/ubi9/ubi cat /etc/app/app.conf
Common mistake

The source must be a path, absolute or starting with ./. -v site:/var/www/html doesn't mount your site directory; it silently creates a named volume called site. Your files never appear and nothing reports an error.

The ro option makes the mount read-only inside the container, which is good practice for configuration. Combine options with commas: :ro,Z.

5SELinux and mounts

Week 1 introduced SELinux's role in isolation: container processes run with the type container_t, and SELinux policy lets them touch only files labeled container_file_t. Files in your home directory are labeled user_home_t. So when you bind-mount ~/site into a container without any label option, SELinux blocks every access, even though ordinary file permissions would allow it.

The symptom is a plain Permission denied, which is confusing precisely because ls -l looks fine. In the httpd image it shows up as 403 Forbidden.

$ ls -ldZ site
drwxr-xr-x. 2 student student unconfined_u:object_r:user_home_t:s0  24 Oct  8 09:14 site
$ sudo ausearch -m avc -ts recent   # shows the denial, if you have sudo

Ask Podman to relabel the directory when it mounts it:

SELinux mount options
OptionNew labelWho can use it
:z (lowercase)container_file_t:s0Any container. Use it when several containers share the directory.
:Z (uppercase)container_file_t:s0:c142,c871Only this container, through its unique category pair. Safest choice for one container.
Never relabel system directories

The relabel is permanent and applies to everything inside the directory. Never use :z or :Z on your whole home directory, /etc, /usr or other system paths. Other programs on the host may stop working. Create a dedicated directory for each container.

Exam habit

Add :Z to every bind mount by default, and switch to :z only when two containers must share the directory. Don't disable SELinux to make a mount work.

6Rootless ownership

Even with the right SELinux label, a rootless container can be refused permission to write to a bind mount. The cause is the user namespace from Week 1. Inside the container, UIDs are mapped onto a range of host UIDs reserved for you in /etc/subuid:

Inside the container
maps to
On the host
UID 0 (root)
→
1000 (student, you)
UID 1
→
100000
UID 27 (mysql)
→
100026
UID 1001 (httpd user)

A directory you create is owned by you, UID 1000 on the host, which the container sees as root. A container whose process runs as root can write to it. But the httpd image runs as UID 1001, and the MariaDB image runs its database as UID 27. To them, your directory belongs to someone else, and writes fail.

There are two fixes. podman unshare runs a command inside your user namespace, where you are root and the container's UIDs exist, so you can hand the directory to the container's user:

$ podman unshare chown 27:27 dbdata
$ ls -ld dbdata
drwxr-xr-x. 2 100026 100026 … dbdata
$ podman unshare cat /proc/self/uid_map
         0       1000          1
         1     100000      65536

Or let Podman do it at start-up with the :U mount option, which changes the directory's ownership to match the container's user: -v ./dbdata:/var/lib/mysql/data:Z,U.

Either way, the directory now belongs to a host UID in your subordinate range, so you can no longer edit its files directly. Use podman unshare to work in it, or podman unshare chown 0:0 to give it back.

8Running a database

Databases are the classic stateful workload, and they pull together everything this week covers. Red Hat's MariaDB image is on registry.redhat.io, so sign in first. It reads its initial user, password and database name from environment variables and stores data in /var/lib/mysql/data.

$ podman login registry.redhat.io
$ podman volume create dbdata
$ podman run -d --name db -p 3306:3306 \
    -e MYSQL_USER=user1 -e MYSQL_PASSWORD=mypa55 -e MYSQL_DATABASE=items \
    -v dbdata:/var/lib/mysql/data \
    registry.redhat.io/rhel9/mariadb-105
$ podman logs db | tail -3

To load data, copy a SQL script into the container and run the client inside it. The client connects through the container's own socket, so no extra networking is involved:

$ podman cp items.sql db:/tmp/items.sql
$ podman exec db sh -c 'mysql -u user1 -pmypa55 items < /tmp/items.sql'
$ podman exec -it db mysql -u user1 -pmypa55 items -e 'SELECT COUNT(*) FROM item;'

Now prove the data is safe: podman rm -f db, run the same podman run command again with the same volume, and query the table. The rows are still there. Because the volume already holds an initialized database, the image skips its first-run setup.

Same image, same data, please

Don't attach a volume initialized by one database version to a much newer image without checking its upgrade notes. And never mount the same database directory into two running database containers; they'll corrupt each other's files.

    10Beyond Red Hat

    Storage in Docker and Kubernetes

    Docker

    • Volumes and bind mounts work the same way: docker volume create, -v name:/path, -v ./dir:/path.
    • Both Docker and Podman also accept the longer, more explicit --mount syntax: --mount type=bind,source=./site,target=/var/www/html. It's easier to read in scripts.
    • On SELinux hosts such as RHEL and Fedora, Docker honors :z and :Z too. On Ubuntu or Debian, which use AppArmor instead, the labels are ignored.
    • With rootful Docker, files a container creates in a bind mount are often owned by root on the host: the opposite of this week's rootless ownership puzzle.
    • Docker Desktop on macOS and Windows passes bind mounts through its virtual machine's file sharing, which is noticeably slower than a native Linux mount.

    Kubernetes preview

    Kubernetes separates asking for storage from providing it, which you'll practice in Week 14:

    • emptyDir: scratch space that lives as long as the pod, like a container's writable layer shared between the pod's containers.
    • hostPath: the Kubernetes version of a bind mount. Generally avoided, because pods move between nodes and the data doesn't follow.
    • PersistentVolumeClaim (PVC): an application's request for storage of a given size and access mode, fulfilled by a PersistentVolume, usually created automatically by a StorageClass.
    • CSI drivers connect Kubernetes to real storage systems: cloud disks such as AWS EBS or Azure Disk, network storage such as NFS, or software-defined storage such as Ceph (OpenShift Data Foundation).
