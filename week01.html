What a container actually is

2The problem containers solve

Every application depends on more than its own code. A Python web app needs a specific Python version, a list of libraries at particular versions, a few system packages, configuration files and environment variables. On the developer's laptop, all of that happens to line up. On the test server, one library is a minor version newer. In production, a system package is missing. The app that "works on my machine" fails everywhere else.

Traditional fixes were slow and fragile: long installation documents, configuration management scripts that try to make every server identical, or one virtual machine per application. A container takes a different approach. You package the application together with its runtime, libraries and default configuration into a single unit called an image. Any Linux host with a container engine can run that image and get the same result, because everything the app needs travels with it.

That one idea pays off in several ways:

  • Consistency. The image a developer tests is byte-for-byte the image that runs in production.
  • Density. Containers share the host kernel, so one server can run dozens or hundreds of them.
  • Speed. A container starts in a fraction of a second because there is no operating system to boot.
  • Isolation. Two apps that need conflicting library versions can run side by side without ever seeing each other.
  • Disposability. Because the image defines the app, you can delete a misbehaving container and start a fresh one instead of repairing it by hand.

That last point is a shift in mindset you will see all semester. Containers are meant to be replaced, not nursed. Any data that has to survive a replacement lives outside the container, which is the subject of Week 5.

3Containers and virtual machines

Virtual machines and containers both let you run several isolated workloads on one physical server, but they draw the isolation boundary in different places. A virtual machine emulates hardware. A hypervisor gives each VM virtual CPUs, memory and disks, and each VM boots its own complete operating system, kernel included.

A container does not emulate anything. It is a normal process running on the host's own kernel. The kernel simply restricts what that process can see and how many resources it can consume. There is exactly one kernel, shared by every container on the host.

When each one fits

Containers win on startup time, size and density. A VM image is measured in gigabytes and boots in tens of seconds; a container image is often tens or hundreds of megabytes and starts almost instantly. VMs win when you need a different kernel or operating system (a Windows workload on a Linux host, for example) or when you need the stronger isolation of a separate kernel. In practice, the two are combined: most containers in the cloud run on Linux hosts that are themselves virtual machines.

Common misconception

A container image based on another Linux distribution does not bring its own kernel. A container built from an Ubuntu image running on a RHEL 9 host is using the RHEL 9 kernel. Only the user-space files (libraries, shell, package manager) come from the image.

4How the kernel builds a container

There is no single "container" feature in Linux. A container engine combines several independent kernel features, each of which solves one part of the isolation problem.

  • Namespaces control what a process can see. Each namespace type gives the process its own private view of one kind of system resource: process IDs, network interfaces, mounted filesystems, the hostname, users and more.
  • Control groups (cgroups) control what a process can use: how much memory, how much CPU time and how many processes. RHEL 9 uses cgroups version 2.
  • SELinux controls what a process is allowed to touch. Container processes run with the container_t type, and each container also gets a unique pair of categories (for example s0:c142,c871), so one container cannot read another container's files even if both run as the same user.
  • Seccomp filters which system calls a process may make, blocking rarely needed and risky ones.
  • Capabilities split root's powers into smaller pieces. Containers start with only a small set, so even "root" inside a container cannot, for example, load kernel modules.

Limits with cgroups
Namespaces hide things, but they don't stop a process from consuming every byte of memory on the host. That is the job of cgroups. When you start a container with a memory limit, the kernel tracks every allocation the container makes. If the container goes over the limit, the kernel's out-of-memory (OOM) killer ends it. Podman reports this as exit code 137, which means the process received signal 9 (128 + 9).

5Images, containers and registries
An image is a read-only template: a stack of filesystem layers plus metadata that says which command to run, which user to run it as, which ports the app listens on and which environment variables to set. A container is a running (or stopped) instance of an image. If an image is a class, a container is an object; you can start many containers from one image.
When a container starts, the engine stacks the image's read-only layers and adds one thin writable layer on top. Any file the container changes is copied up into that writable layer (copy-on-write). Delete the container and the writable layer goes with it; the image is untouched. This is why changes made inside a running container disappear when you replace it.
Naming an image
A fully qualified image name has four parts:

 
registry.access.redhat.com/ubi9/httpd-24:latest
└──────── registry ───────┘└ namespace ┘└ repo ┘└ tag ┘

 
  • The registry is the server that stores images, such as registry.access.redhat.com, registry.redhat.io or quay.io.
  • The namespace groups related repositories, usually by organization or product line.
  • The repository holds every version of one image.
  • The tag labels one version. If you leave it off, latest is assumed.
Tags are convenient but mutable: the publisher can move latest to a new build at any time. Every image also has a digest, a SHA-256 hash of its contents such as @sha256:4c1b…. A digest can never point to different contents, so it is the way to guarantee you get exactly the image you tested.
Open standards
Image and container formats are defined by the Open Container Initiative (OCI). Because Podman, Docker, Kubernetes and OpenShift all follow the OCI specifications, an image built with one tool runs on all the others. Under the hood, Podman hands the actual work of creating the container to a low-level OCI runtime such as crun or runc.
Exam habit
Get used to typing fully qualified image names now. Short names such as httpd-24 make Podman search a list of registries, which can be ambiguous, can prompt you to choose and may pull an image from somewhere you didn't intend.
6Podman, Buildah and Skopeo
Red Hat Enterprise Linux ships three complementary open source tools for working with containers. All three are in the default RHEL 9 repositories.
The three container tools and their jobs
ToolMain jobExample
PodmanRun and manage containers, pods, images, networks and volumes. Also builds images using Buildah's code.podman run, podman ps
BuildahBuild OCI images, from a Containerfile or step by step from the command line.buildah bud, buildah from
SkopeoInspect, copy and sign images directly in registries, without pulling them into local storage.skopeo inspect, skopeo copy
Daemonless
Some container engines run a central background service (a daemon), usually as root, and every command you type is a request sent to it. Podman has no daemon. When you run podman run, Podman itself sets up the container and then exits, leaving a small monitor process called conmon to watch the container. There is no single privileged service that, if compromised or crashed, takes every container with it. It also means containers integrate cleanly with systemd, which you'll use later to start containers at boot.
Rootless
Podman can run containers as an ordinary user. A user namespace maps "root" inside the container to your own unprivileged account on the host, using the ID ranges listed in /etc/subuid and /etc/subgid. If an attacker escapes a rootless container, they land on the host as you, not as root. You'll do almost all of this course's Podman work rootless.
Compatible commands
Podman's command line deliberately mirrors Docker's, so most Docker tutorials work if you replace docker with podman. Podman adds one idea Docker doesn't have: the pod, a group of containers that share a network namespace. Pods are the same concept Kubernetes uses, which makes Podman a natural stepping stone to OpenShift.

 
$ skopeo inspect docker://registry.access.redhat.com/ubi9/ubi
{
    "Name": "registry.access.redhat.com/ubi9/ubi",

7Beyond one host
Podman is excellent on a single machine. Production systems, though, run hundreds of containers across many servers, and they need answers to questions a single host can't provide. Which server has room for this container? What happens when a server fails at 3 a.m.? How do we run five copies of the web tier and send traffic evenly across them? How do we roll out a new version without downtime, and roll back if it's broken?
A container orchestrator answers those questions. Kubernetes is the open source standard. You describe the state you want ("three replicas of this image, reachable on this port, with this much memory each") and Kubernetes continuously works to make the cluster match: scheduling containers onto nodes, restarting them when they fail, and replacing them during updates.
Red Hat OpenShift is a Kubernetes distribution. Everything you learn about Kubernetes applies to it, and it adds a web console, routes for exposing applications, built-in image builds, an integrated registry, and stricter security defaults. One of those defaults matters early: by default OpenShift runs containers as an arbitrary, non-root user ID. Images that assume they run as root often fail on OpenShift, which is one reason this course teaches you to build images carefully in Weeks 3 and 4.
You'll get your first look at a cluster in Week 8, and the entire second half of the course (Weeks 10 to 15) is about operating applications on OpenShift.
8Beyond Red Hat
The wider container world
This course uses Red Hat's tools because they're what the certifications test, but job postings will just as often ask for Docker and Kubernetes. The good news: because everything follows the OCI standards, the concepts you learn here transfer almost one for one. Here is who's who.

Orchestrators
Kubernetes is the open source project, governed by the Cloud Native Computing Foundation (CNCF). Most people run a distribution or a managed service rather than assembling it themselves:
  • Managed cloud services: Amazon EKS, Azure AKS and Google GKE. Red Hat OpenShift is also offered as a managed service on the big clouds (ROSA on AWS, ARO on Azure).
  • Distributions you install: Red Hat OpenShift, SUSE Rancher (RKE2), and the lightweight k3s for edge devices.
  • Local learning clusters: minikube, kind (Kubernetes in Docker or Podman) and OpenShift Local.
Other orchestrators exist, such as Docker Swarm and HashiCorp Nomad, but Kubernetes is the industry standard, and it's what Weeks 8 to 15 teach.
Exam versus job market
Red Hat's EX188 and EX280 exams test Podman and OpenShift specifically. On your resume, list the underlying skills too: "OCI containers (Podman, Docker)" and "Kubernetes (OpenShift)".
