1Goals

By the end of this module you should be able to:

  • Explain how a rolling update replaces pods, and how maxSurge, maxUnavailable and readiness control it.
  • Choose between RollingUpdate and Recreate.
  • Update a deployment's image or configuration, watch the rollout, and read its history.
  • Roll back a bad update, and pause a deployment to batch several changes.
  • Explain how image references and image stream triggers affect updates.
  • Deploy, configure, scale and update a complete application on OpenShift under time pressure.

2How rolling updates work

When anything in a deployment's pod template changes (image, environment, volumes, probes, resources), the deployment creates a new ReplicaSet and moves pods from the old one to the new one. With the default RollingUpdate strategy, it does this gradually:

  • maxSurge: how many pods above the desired count may exist during the update (default 25%, rounded up).
  • maxUnavailable: how many pods below the desired count may be unavailable (default 25%, rounded down).

The controller only removes an old pod when enough new pods are ready. That's why the readiness probe from Module 14 matters so much: if version 2 never becomes ready, the rollout stalls with most version 1 pods still serving users. A bad release becomes a stuck rollout instead of an outage.

The Recreate strategy stops every old pod first, then starts the new ones. It causes downtime, so use it only when two versions must never run at once: an RWO volume that only one pod can mount, or a database schema change the old version can't handle.

$ oc patch deployment/web -p '{"spec":{"strategy":{"rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}'
$ oc patch deployment/web -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'

4Triggering updates

Any change to the pod template starts a rollout. The commands you'll use:

$ oc set image deployment/web web=registry.access.redhat.com/ubi9/httpd-24:1
$ oc set env deployment/web THEME=dark
$ oc apply -f web.yaml                  # if the template in the file changed
$ oc rollout restart deployment/web     # new pods, same template
$ oc rollout status deployment/web

Image references and updates

Kubernetes compares the template text, not the image contents. If you push a new build to the same tag, :latest or :1, nothing in the template changes, so nothing rolls out. Nodes that already have the old image may even keep using it, depending on the imagePullPolicy. Use a new tag or a digest for each release, so every change is visible in the template and in the history.

Image streams and triggers

OpenShift adds image streams: named pointers to images, inside your project, that can track a registry tag. An image trigger on a deployment watches an image stream tag and updates the deployment whenever the tag moves to a new image, automatically rolling out new builds.

$ oc import-image web:1 --from=registry.access.redhat.com/ubi9/httpd-24:1 --confirm --scheduled
$ oc set triggers deployment/web --from-image=web:1 -c web
$ oc tag web:1 web:prod               # promote by moving a tag

5History, rollback and pause

Each template change is a numbered revision, kept as an old ReplicaSet scaled to zero (the last ten by default, set by revisionHistoryLimit). That's what makes rollback fast: the old pod template is still there.

$ oc rollout history deployment/web
deployment.apps/web
REVISION  CHANGE-CAUSE
1         <none>
2         update to httpd 2.4 build 1
$ oc annotate deployment/web kubernetes.io/change-cause="update to httpd 2.4 build 1"
$ oc rollout history deployment/web --revision=2
$ oc rollout undo deployment/web                    # back to the previous revision
$ oc rollout undo deployment/web --to-revision=1

A rollback is itself a new revision, copying the old template. To make several changes without triggering a rollout for each one, pause the deployment, make them all, then resume:

$ oc rollout pause deployment/web
$ oc set image deployment/web web=…:1-351
$ oc set resources deployment/web --limits=memory=512Mi
$ oc rollout resume deployment/web                  # one rollout with both changes
Rollback isn't a time machine

Undo restores the pod template only. Data the new version wrote, database migrations it ran, ConfigMaps or Secrets you edited, and PVC contents all stay as they are. Plan releases so the previous version can still run against the new data.

6About the final practicals

The final lab practicals in Module 15 measure Outcomes 4 and 5: deploying, configuring and managing an application on OpenShift (networking, configuration data, secrets and storage), and keeping it reliable with probes, resource limits, autoscaling and controlled updates with rollback. Together they are 30% of your grade. As always, there's no written exam: you'll perform real tasks in a live cluster.

  • The deadline is firm; exceptions need your instructor's written approval in advance.
  • It's individual work, and AI tools may not be used to complete the tasks. oc explain, --help and the product documentation are your references unless your instructor says otherwise.
  • Report environment problems immediately.

The strategy from the midterm still applies: read everything first, budget time per task, copy names exactly, verify every task as you finish it, and check the final state before grading. Two cluster-specific additions:

  • Confirm the project and user before every task: oc whoami, oc project.
  • Wait for rollouts. After every change, oc rollout status before you test. Testing a half-finished rollout gives misleading results.

    10Beyond Red Hat

    Releasing software elsewhere

    • Progressive delivery. Argo Rollouts and Flagger extend deployments with canary releases (send 5% of traffic to the new version, watch error rates, then increase) and blue-green releases (run both, switch all traffic at once). On OpenShift, routes can split traffic between services by weight for the same purpose.
    • Helm packages an application's manifests as a chart. helm upgrade and helm rollback manage releases as a unit, including ConfigMaps and services, not just one deployment.
    • GitOps. With Argo CD or Flux, every release is a Git commit and a rollback is a git revert. The cluster follows the repository.
    • CI/CD pipelines such as GitHub Actions, GitLab CI, Jenkins or Tekton (OpenShift Pipelines) build an image, tag it with the commit, push it, and update the deployment or the Git repository automatically.
    • Feature flags separate deploying code from turning features on, so a risky feature can be switched off without any rollback.
    • Your next step: the EX280 exam builds on everything in Modules 10 to 15, adding cluster administration such as users, quotas, network policies and operators.
