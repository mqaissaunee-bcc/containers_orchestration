1Goals

By the end of this week you should be able to:

  • Start containers in the foreground, in the background and interactively, with and without automatic removal.
  • List, stop, start, restart and remove containers, and explain each lifecycle state.
  • Read container logs, run commands inside a running container, copy files in and query details with podman inspect.
  • Publish container ports to the host, and explain the rootless rule for ports below 1024.
  • Create a user-defined network so containers can reach each other by name.

2Running a container

The workhorse command is podman run. In its simplest form you give it an image and, optionally, a command to run instead of the image's default:

$ podman run registry.access.redhat.com/ubi9/ubi echo "Hello, containers"
Trying to pull registry.access.redhat.com/ubi9/ubi:latest...
Getting image source signatures
Copying blob 7c5f…  done
Copying config 3a1b…  done
Writing manifest to image destination
Hello, containers

Several things happened. Podman didn't have the image, so it pulled it from the registry. It created a container, ran echo inside it, printed the output and then the container exited, because its only process finished. A container lives exactly as long as its main process. That one rule explains a surprising amount of container behavior.

Options you'll use constantly

Common podman run options
OptionWhat it does
-d, --detachRun in the background and print the container ID. Use it for servers.
--name webGive the container a name you can type. Otherwise Podman invents one such as quirky_turing.
-itInteractive with a terminal (-i keeps standard input open, -t allocates a terminal). Use it to get a shell.
--rmRemove the container automatically when it exits. Good for one-off commands.
-p 8080:8080Publish a port: host port:container port.
-e NAME=valueSet an environment variable, the usual way to configure a containerized app.
--network app-netAttach the container to a specific network.

Here's a typical server start. The container runs in the background and Podman prints its full ID:

$ podman run -d --name web -p 8080:8080 registry.access.redhat.com/ubi9/httpd-24
8d2f6c1e9b0a4f7d…
$ podman ps
CONTAINER ID  IMAGE                                            COMMAND               CREATED        STATUS        PORTS                   NAMES
8d2f6c1e9b0a  registry.access.redhat.com/ubi9/httpd-24:latest  /usr/bin/run-http...  5 seconds ago  Up 5 seconds  0.0.0.0:8080->8080/tcp  web
Common mistake

podman run -d registry.access.redhat.com/ubi9/ubi appears to do nothing: podman ps shows no container. The image's default command is a shell, a shell with no input exits immediately, and the container exits with it. Run podman ps -a to see it with status Exited (0). Detach only things that keep running, such as servers.

Decode a podman run command

Type or paste any podman run command to see what each part means. Try changing the example.

3The container lifecycle

A container moves through a small set of states. podman run is really two steps in one: podman create makes the container (allocating its writable layer and configuration) and podman start launches its main process.

  • Created: configured, but the process has never run.
  • Running: the main process is alive.
  • Paused: every process is frozen in place using the cgroup freezer. Memory is kept; nothing executes.
  • Exited: the main process ended. The container and its writable layer still exist, so you can read its logs or start it again.
  • Removed: gone, along with its writable layer.

podman stop asks politely: it sends SIGTERM, waits (10 seconds by default) and only then sends SIGKILL. podman kill sends SIGKILL immediately, which gives the app no chance to clean up.

Drive a container through its states

Only the commands that make sense in the current state will work. Try the ones that don't, too, to see the error you'd get.

  • no container
  • created
  • running
  • paused
  • exited

4Looking inside a container

When a containerized app misbehaves, four commands do most of the investigating. You'll go deeper in Week 6, but you need them from day one.

Logs

Anything the main process writes to standard output or standard error is captured. Well-built images send their logs there instead of to files inside the container. Add -f to follow new lines as they arrive, and --tail 20 to see only the end.

$ podman logs web
$ podman logs -f --tail 20 web

Exec

podman exec starts an additional process inside a running container. It shares that container's namespaces, so it sees the same files, network and processes.

$ podman exec web cat /etc/redhat-release
Red Hat Enterprise Linux release 9.4 (Plow)
$ podman exec -it web /bin/bash
bash-5.1$ whoami
default
bash-5.1$ exit

The httpd image runs as an unprivileged user named default (UID 1001), not as root. That design choice is what lets it run on OpenShift later.

Inspect

podman inspect prints everything Podman knows about a container or image as JSON: state, exit code, IP address, mounts, environment and more. The --format option takes a Go template, so you can pull out one value without scrolling through hundreds of lines.

$ podman inspect --format '{{.State.Status}}' web
running
$ podman inspect --format '{{.NetworkSettings.IPAddress}}' web

Copy

podman cp copies files between the host and a container, in either direction. It's handy for pulling out a log file or dropping in a test page. Remember the change lives in the container's writable layer and disappears when the container is removed; you'll learn the permanent fixes (custom images and volumes) in Weeks 4 and 5.

$ podman cp index.html web:/var/www/html/index.html
$ podman cp web:/etc/httpd/conf/httpd.conf .

5Ports and networks

A container has its own network namespace, so a server listening on port 8080 inside it is invisible from outside until you publish the port. The -p option maps a host port to a container port. The host side comes first:

$ podman run -d --name web -p 8080:8080 registry.access.redhat.com/ubi9/httpd-24
$ podman port web
8080/tcp -> 0.0.0.0:8080
$ curl http://localhost:8080

The two numbers don't have to match. -p 9000:8080 lets you reach the same server at localhost:9000, which is how you run two copies of one image side by side. Only one container can hold a given host port at a time.

The rootless port rule

By default, Linux reserves ports below 1024 for privileged processes. A rootless container therefore cannot publish host port 80 or 443:

$ podman run -d -p 80:8080 registry.access.redhat.com/ubi9/httpd-24
Error: rootlessport cannot expose privileged port 80, you can add 'net.ipv4.ip_unprivileged_port_start=80' to /etc/sysctl.conf (currently 1024), or choose a larger port number (>= 1024)

The fix in this course is simply to use a host port of 1024 or above. This is also why Red Hat's images listen on 8080 rather than 80 inside the container: an unprivileged process can bind it.

Container-to-container traffic

Rootless containers share a private network that Podman sets up for your user. Every container you start without --network joins the default network, named podman. Containers on it can reach each other by IP address, but the default network does not provide name resolution. IP addresses change every time a container is recreated, so relying on them is fragile.

Create your own network instead. Podman runs a small DNS service for every user-defined network, so containers on it can find each other by container name:

$ podman network create app-net
$ podman run -d --name web --network app-net registry.access.redhat.com/ubi9/httpd-24
$ podman run --rm --network app-net registry.access.redhat.com/ubi9/ubi curl -s http://web:8080

Notice the second container reached web on port 8080 without any -p. Publishing is only needed for traffic coming from outside Podman's network.

Exam habit

When two containers need to talk, put them on one user-defined network and use container names as hostnames. Reach for -p only for the ports a person or another machine needs to reach from the host.

Configuring with environment variables

Many images expect settings as environment variables. A database image, for example, typically needs a user, password and database name before it will start. Red Hat's database images live on registry.redhat.io, which requires you to sign in first with podman login registry.redhat.io:

$ podman run -d --name db --network app-net \
  -e MYSQL_USER=user1 -e MYSQL_PASSWORD=mypa55 -e MYSQL_DATABASE=items \
  registry.redhat.io/rhel9/mariadb-105

Each image documents the variables it reads. Check with skopeo inspect or the image's page in the Red Hat Ecosystem Catalog.
