1Goals

By the end of this week you should be able to:

  • Describe public and private registries, including the Red Hat registries, and choose a trustworthy base image.
  • Read any image reference and identify its registry, namespace, repository, tag and digest.
  • Explain why tags can change and digests cannot, and pin an image to an exact version.
  • Inspect remote images with skopeo and local images with podman image inspect.
  • Sign in to a registry, tag an image for it, push it, pull it back, and copy images between registries.
  • List, remove and prune local images, and know where rootless Podman stores them.

2Where images come from

A registry is a server that stores images and hands them out over HTTPS. Some registries are public and anyone can pull from them. Others are private: a company runs its own registry, or rents private repositories from a hosted service, so that only its own people and systems can pull its images.

In this course you'll meet three registries most often:

  • registry.access.redhat.com serves Red Hat images that need no sign-in, including the Universal Base Images.
  • registry.redhat.io serves Red Hat's supported product images, such as the database images. You must sign in with a Red Hat account.
  • quay.io is a hosted registry where you can keep your own public or private repositories.

You can browse Red Hat's published images, their tags and their security status in the Red Hat Ecosystem Catalog at catalog.redhat.com.

Universal Base Images

The Universal Base Images (UBI) are RHEL-based images that anyone can use and redistribute, even outside a Red Hat subscription. They come in several sizes:

UBI 9 image variants
ImageWhat's insideUse it when
ubi9/ubiFull user space with dnfYou need to install packages easily.
ubi9/ubi-minimalSmaller set of packages, with microdnfYou want a smaller image and can live with a lighter package tool.

How Podman finds a registry

Podman's registry settings live in /etc/containers/registries.conf, and you can override them per user in ~/.config/containers/registries.conf. The unqualified-search-registries list tells Podman where to look when you give a short name such as httpd-24. Files in /etc/containers/registries.conf.d/ define short-name aliases that map common short names to one specific image.

Short names are convenient, but if a name exists in more than one search registry Podman has to guess or ask you. An attacker could also publish a look-alike image under the same name in another registry. That's why this course, and Red Hat's exams, expect fully qualified names.

Trust is a choice

Pulling an image means running someone else's software. Prefer images from a vendor you trust, check their published security information, and be wary of popular-sounding images from unknown accounts.

3Names, tags and digests

Week 1 introduced the parts of a fully qualified name. Practice reading them until it's automatic, because you'll type image references in nearly every command this semester.

Image reference reader

    Try httpd-24, quay.io/student/myapp, registry.example.com:5000/team/api:v2 or a reference ending in @sha256:….

    Tags move. Digests don't.

    A tag is a label the publisher can point at any build at any time. Red Hat images usually carry several tags at once. Using the httpd image as an example: latest follows the newest build of any version, 1 follows the newest build of major version 1, and a release tag such as 1-338 names one specific build. By convention, release tags aren't reused, but nothing in the registry enforces that.

    A digest is different in kind. It's the SHA-256 hash of the image manifest, so it is computed from the image itself. If the content changes, the digest changes. Pull image@sha256:… and you get exactly the bytes you tested, forever.

    Watch tags drift

    You deployed four references on day one. Each time the publisher ships a new build, see which references now give you something different.

      What each reference resolves to now
      Reference you usedGets you nowSame as day one?

      Exam habit

      When a task names a specific version, use that exact tag or digest. Never rely on latest to mean "the version I was told to use".

      4Look before you pull

      Images can be hundreds of megabytes. Skopeo lets you read an image's metadata straight from the registry first: its digest, every tag in the repository, when it was built, its labels, its default user and command. Note the docker:// prefix. Skopeo works with several transports, and docker:// means "a registry that speaks the standard distribution API", whatever software actually runs it.

      $ skopeo inspect docker://registry.access.redhat.com/ubi9/httpd-24
$ skopeo inspect --format '{{.Digest}}' docker://registry.access.redhat.com/ubi9/httpd-24:1-338
$ skopeo list-tags docker://registry.access.redhat.com/ubi9/ubi

      Once an image is local, podman image inspect shows the same kind of detail, plus podman history lists the layers and the instruction that created each one. Next week you'll create those layers yourself.

      $ podman image inspect --format '{{.Config.User}}' registry.access.redhat.com/ubi9/httpd-24
1001
$ podman history registry.access.redhat.com/ubi9/httpd-24

      Checking .Config.User before you deploy is a good habit: an image that runs as root will need changes before it can run on OpenShift.

      5Signing in to registries

      Private repositories, and every push, require you to authenticate. podman login asks for a username and password and stores a token. Rootless Podman keeps it by default in $XDG_RUNTIME_DIR/containers/auth.json. That directory lives in memory and is cleared when you fully log out of the system, so you'll log in again in each new session. Podman, Buildah and Skopeo all read the same file, so one login works for all three.

      $ podman login registry.redhat.io
Username: your-redhat-login
Password:
Login Succeeded!
$ podman login --get-login registry.redhat.io
your-redhat-login
$ podman logout registry.redhat.io
      Keep passwords out of history

      Don't type podman login -p MyPassword; the password ends up in your shell history and the process list. In scripts, read it from a protected file with --password-stdin. Many registries, including Quay and the Red Hat registry, also let you create limited robot or service accounts for automation.

      6Tagging, pushing and copying

      To publish an image, you first give it a name that includes your registry and namespace. podman tag adds that name to an image you already have. It copies nothing: both names now point to the same image ID. Then podman push uploads it.

      $ podman tag registry.access.redhat.com/ubi9/ubi:9.4 quay.io/student/myubi:v1
$ podman images
REPOSITORY                           TAG   IMAGE ID      …
registry.access.redhat.com/ubi9/ubi  9.4   4c1b2e7f90aa  …
quay.io/student/myubi                v1    4c1b2e7f90aa  …
$ podman push quay.io/student/myubi:v1

      If you tag with a name that has no registry, such as myubi:v1, Podman stores it as localhost/myubi:v1. That works for local testing but there's nowhere to push it.

      Registry to registry

      Moving an image between registries with Podman means pull, tag, push, using local disk along the way. skopeo copy does it in one step, streaming from source to destination without touching local storage. It's the standard way to mirror images into a private registry.

      $ skopeo copy docker://registry.access.redhat.com/ubi9/httpd-24:1-338 docker://quay.io/student/httpd:1-338

      No network? Use an archive.

      For a disconnected system, save the image to a tar file, carry it over, and load it on the other side.

      $ podman save -o myubi.tar quay.io/student/myubi:v1
$ podman load -i myubi.tar

      7Managing local storage

      Rootless Podman keeps images and containers under ~/.local/share/containers/storage. Root uses /var/lib/containers/storage. They are completely separate, which is why an image you pulled with sudo podman doesn't appear in your own podman images.

      Images pile up quickly. Three commands keep storage under control:

      • podman rmi NAME removes one tag. The image data is deleted only when no tags point to it. Podman refuses to remove an image a container still uses unless you add -f, which also removes those containers.
      • podman image prune removes dangling images: ones that have lost all their tags, usually because a newer build took the name.
      • podman image prune -a removes every image that no container is using. Expect to re-pull them later.
      $ podman images --digests
$ podman rmi quay.io/student/myubi:v1
$ podman image prune -a
$ podman system df     # how much space images, containers and volumes use

        9Beyond Red Hat

        Other registries and image tools

        Container registries outside Red Hat
        RegistryHost nameNotes
        Docker Hubdocker.ioThe largest public registry and Docker's default. "Official images" live in the library namespace, so nginx means docker.io/library/nginx. Anonymous pulls are rate-limited.
        GitHub Container Registryghcr.ioImages stored next to the code that builds them, with GitHub permissions.
        Amazon ECR, Google Artifact Registry, Azure Container RegistryPer-account host namesPrivate registries in each cloud, integrated with that cloud's identity and Kubernetes service.
        GitLab Container RegistryYour GitLab hostBuilt into GitLab projects and CI pipelines.
        HarborSelf-hostedA CNCF project for running your own registry, with scanning and replication. Project Quay is the self-hosted version of quay.io.
        Docker-style short names

        Tutorials written for Docker say FROM nginx or docker pull redis, relying on Docker's default of Docker Hub. With Podman, write the full name, docker.io/library/nginx, or Podman may search a different registry first.

        Tools that do what Skopeo does

        • crane (from Google's go-containerregistry) and regctl inspect and copy images between registries.
        • oras stores other artifacts, such as Helm charts or signatures, in OCI registries.

        Trusting images

        • Signing: Sigstore's cosign signs images and verifies signatures. Podman and Skopeo can enforce signature policies too.
        • Scanning: Trivy, Grype and Clair (built into Quay) list known vulnerabilities in an image's packages. Many teams run a scanner in their build pipeline and block images with critical findings.
