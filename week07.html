1Goals

  • Run a container as a systemd service with a Quadlet file.

2One app, many containers

The guiding rule is one main process per container. A web application and its database go in separate containers, built from separate images. That way you can update the web tier without touching the database, give each the resources it needs, and replace one without restarting the other.

You already know how to connect them by hand: create a network, create a volume, then run each container with the right name, network, environment, ports and mounts. It works, but it lives only in your shell history. Rebuild the environment next month, or hand it to a teammate, and you're retyping long commands from memory.

Compose replaces those commands with a YAML file that describes the finished application. The file is short, readable, and goes into version control next to your code. One command creates everything it describes; another removes it.

3The Compose file

A Compose file, conventionally compose.yaml, follows the open Compose Specification. Its top level has up to three main keys: services (the containers), volumes (named volumes) and networks.

services:
  db:
    image: registry.redhat.io/rhel9/mariadb-105
    environment:
      MYSQL_USER: user1
      MYSQL_PASSWORD: mypa55
      MYSQL_DATABASE: items
    volumes:
      - dbdata:/var/lib/mysql/data
  web:
    image: registry.access.redhat.com/ubi9/httpd-24
    ports:
      - "8080:8080"
    volumes:
      - ./site:/var/www/html:Z
    depends_on:
      - db

volumes:
  dbdata: {}

Each service maps directly to podman run options you already know:

Compose service keys and podman run options
Compose keypodman run equivalent
image:The image argument
build: .podman build first, then run the result
ports:-p
environment:-e (as a map or as a list of KEY=value)
volumes:-v
networks:--network
command:Arguments after the image, replacing CMD
user:--user
container_name:--name (otherwise Compose generates one)

What Compose does for you

  • A private network with DNS. If you don't define networks, Compose creates one named project_default and puts every service on it. Each container is reachable by its service name, so the web tier connects to the host db.
  • Prefixed names. The project name defaults to the directory name. Volumes and networks get it as a prefix (myapp_dbdata), and containers are named like myapp_db_1. That keeps two projects on one host from colliding.
  • Variable substitution. ${MYSQL_PASSWORD} in the file is filled from your environment or from a .env file beside it, which keeps passwords out of the file you commit.
YAML is picky

Indentation is structure: use spaces, never tabs, and line up keys at the same level exactly. Quote port mappings ("8080:8080") so YAML can't misread them as numbers.

4Compose commands

RHEL provides podman-compose, a tool that reads Compose files and runs the equivalent Podman commands. It prints each command as it goes, which is a good way to check your understanding. Recent Podman versions also include podman compose, which hands the work to an installed Compose provider.

$ podman-compose up -d        # create networks, volumes and containers, in the background
$ podman-compose ps           # this project's containers
$ podman-compose logs web     # one service's logs
$ podman-compose down         # stop and remove containers and networks; keep volumes
$ podman-compose down -v      # also remove named volumes (deletes the data)
$ podman-compose -f other.yaml up -d

Because Compose just runs Podman, every tool from earlier weeks still works: podman ps, podman logs myapp_db_1, podman exec, podman inspect.

5Startup order and readiness

depends_on tells Compose to start the database container before the web container. It doesn't wait for the database to be ready. A database can take several seconds to initialize after its container starts, and an app that connects immediately fails.

There are two complementary fixes. First, give the dependency a health check, and make the dependent service wait for it to pass with condition: service_healthy (supported by Docker Compose and by recent podman-compose releases). Second, and more robust, write applications that retry their connections, because in production a database can restart at any time, not just at startup.

Watch the race

  db:
    image: registry.redhat.io/rhel9/mariadb-105
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h localhost"]
      interval: 5s
      retries: 10
  web:
    depends_on:
      db:
        condition: service_healthy

    7Pods

    A pod is a group of containers that share one network namespace, and therefore one IP address and one localhost. A container in a pod can reach its neighbor at localhost:8080, with no DNS involved. Each pod also has a tiny infra container whose only job is to hold those shared namespaces open.

    Pods suit tightly coupled helpers: a web server plus a sidecar that refreshes its content, or an app plus a proxy in front of it. Unrelated services, like a web tier and its database, are better as separate containers or separate pods, so you can scale and replace them independently.

    Because the network belongs to the pod, ports are published on the pod, not on its containers:

    $ podman pod create --name webpod -p 9090:8080
$ podman run -d --pod webpod --name webpod-web registry.access.redhat.com/ubi9/httpd-24
$ podman pod ps
$ podman ps --pod

    The bridge to Kubernetes

    The pod is the smallest unit Kubernetes runs, and Podman pods are the same idea. Podman can write Kubernetes YAML describing a pod, and can run Kubernetes YAML locally:

    $ podman kube generate webpod -f webpod.yaml
$ podman pod rm -f webpod
$ podman kube play webpod.yaml          # recreate it from the YAML
$ podman kube play --down webpod.yaml   # tear it down

    You'll meet this exact YAML structure on OpenShift next week.

    8Running at boot with Quadlet

    Podman has no daemon to restart containers after a reboot. Instead, it hands that job to systemd, the same service manager that starts everything else on RHEL. Quadlet, included since Podman 4.4, lets you describe a container in a small unit-style file; systemd turns it into a service.

    # ~/.config/containers/systemd/web.container
[Unit]
Description=NETW 112 web server

[Container]
Image=registry.access.redhat.com/ubi9/httpd-24
PublishPort=8080:8080
Volume=web-data:/var/www/html

[Service]
Restart=always

[Install]
WantedBy=default.target
    $ systemctl --user daemon-reload       # Quadlet generates web.service
$ systemctl --user start web.service
$ systemctl --user status web.service
$ loginctl enable-linger               # keep your user services running when you're logged out

    Quadlet replaces the older podman generate systemd command, which is deprecated. Quadlet also has .volume, .network, .pod and .kube file types.

      10Beyond Red Hat

      Compose in the wider world

      • Docker Compose is the most widely used Compose implementation. Version 2, run as docker compose (with a space), is built into current Docker releases; the old Python docker-compose is retired. The same compose.yaml works with both Docker Compose and podman-compose for everything in this chapter.
      • Docker Compose adds conveniences such as profiles (optional services enabled with --profile), --scale web=3, and compose watch, which syncs code changes into running containers during development.
      • Older files begin with a version: "3.8" line. The Compose Specification made that key obsolete; current tools ignore it or warn about it.
      • Kompose converts a Compose file into Kubernetes manifests. It's a reasonable starting point, but real clusters need things Compose has no words for, such as replicas, probes and resource limits.
      • On Kubernetes, multi-component applications are usually packaged with Helm charts or Kustomize overlays rather than Compose.
      • Docker has no Quadlet equivalent. It restarts containers itself through its daemon, using restart: always in Compose or --restart always on the command line.

      Before you start

      Watch for these during the lab

      • Run Compose commands from the directory that holds the Compose file, or pass -f. The directory name becomes the project name, which prefixes container, network and volume names the grader may check.
      • When a service fails, go straight to podman-compose logs SERVICE or podman logs CONTAINER, then apply last week's method.
      • After editing the file, run podman-compose up -d again. Validate first with podman-compose config if the YAML is new.
      • Don't use down -v unless you mean to delete the data.
