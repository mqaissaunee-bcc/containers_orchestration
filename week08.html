From one host to a cluster

  • Explain what pods, deployments, replica sets, services, routes and projects are for, and how labels connect them.
  • Name what OpenShift adds to Kubernetes.

2What one host can't do

Everything so far ran on your workstation. That's fine for development, but production asks questions a single host can't answer:

  • Failure. The server dies at 3 a.m. Who restarts the containers, and where?
  • Placement. Fifty containers, ten servers. Which container goes where, given each one's CPU and memory needs?
  • Scale. Traffic triples on Monday morning. How do you go from three copies of the web tier to nine, and back?
  • Discovery and load balancing. Copies come and go with changing IP addresses. How do clients find a working copy?
  • Updates. How do you replace version 1 with version 2 without downtime, and go back if version 2 is broken?

A container orchestrator answers all of them, and Kubernetes is the industry standard. Red Hat OpenShift is a Kubernetes distribution: everything you learn about Kubernetes applies to it, and it adds tools on top.

3How Kubernetes works

A cluster is a set of machines, called nodes, split into two roles:

Control plane

API server
The front door. Every command, from you, the web console or other components, is an API request to it.
etcd
The database that stores the cluster's desired and current state.
Scheduler
Chooses a node for each new pod, based on available resources and rules.
Controller manager
Runs the controllers that compare desired state with reality and fix differences.

Worker nodes

kubelet
The agent on each node. It starts and watches the pods assigned to that node.
Container runtime
Actually runs the containers. On OpenShift that's CRI-O, a sibling of Podman.
Network plugin
Gives every pod an IP address and connects pods across nodes (OVN-Kubernetes on OpenShift).

Declare, don't command

With Podman you give orders: run this, stop that. With Kubernetes you declare the state you want, such as "three copies of this image, each with 256 MiB of memory", and store it in the cluster. Controllers then run a loop forever:

  1. Observe the current state.
  2. Compare it with the desired state.
  3. Act to close any gap: start a pod, delete one, move one.

That loop, called reconciliation, is why deleting a pod managed by a deployment doesn't make it go away: the controller notices one copy is missing and creates a replacement within seconds. To really reduce the count, you change the desired state.

5The core resources

Everything in Kubernetes is a resource: an object with a kind, a name, a specification of what you want, and a status reporting what exists. The ones you'll use constantly:

Core Kubernetes and OpenShift resources
ResourceWhat it isPodman analogy
PodOne or more containers that share a network namespace and storage, scheduled together onto one node. The smallest unit Kubernetes runs.A Podman pod
DeploymentDeclares an image and a replica count, and manages updates. It creates a ReplicaSet, which creates the pods.A podman run command that reruns itself
ServiceA stable virtual IP address and DNS name that load-balances across the pods matching a label selector.A user-defined network's DNS name, plus load balancing
Route (OpenShift)Exposes a service outside the cluster with a host name, through the cluster's router.-p port publishing
Project / namespaceA named space that isolates resources, permissions and quotas. In OpenShift a project is a namespace with extra metadata.A Compose project

Labels hold it together

Resources find each other by labels, simple key-value tags such as app=web. A deployment stamps app=web on every pod it creates; the service named web selects pods with app=web. No list of pod names or IP addresses is stored anywhere, which is why pods can come and go freely.

Resources are YAML

Every resource can be written as YAML and applied with oc apply -f. Commands such as oc create deployment are shortcuts that generate this for you. Compare it with the pod YAML Podman generated last week:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: httpd
        image: registry.access.redhat.com/ubi9/httpd-24:1-338
        ports:
        - containerPort: 8080

The template section is a pod specification. The deployment uses it as a cookie cutter for every replica.

6What OpenShift adds

  • A web console with a Developer perspective (topology views, deploying from images or Git) and an Administrator perspective (cluster-wide resources and settings).
  • Routes and a built-in router, so exposing an application is one command.
  • Builds, including Source-to-Image (S2I), which turn source code or a Containerfile into an image inside the cluster, and image streams that track image versions.
  • An integrated image registry for images built in the cluster.
  • Projects with self-service creation, quotas and role-based access.
  • Stricter security defaults. The restricted-v2 security context constraint (SCC) runs every container with a random, high UID in group 0, and drops privileges. This is where your Week 4 habits pay off.
  • Operators and OperatorHub for installing and running complex software, plus built-in monitoring and logging.
  • The oc client, which includes every kubectl command plus OpenShift ones such as oc login, oc new-project, oc new-app and oc expose.
Why that nginx image crashes

Many popular images on Docker Hub assume they run as root: they write to directories owned by root or bind port 80. On OpenShift they run as a random non-root UID and fail with "Permission denied", then sit in CrashLoopBackOff. Use images built for non-root operation, like Red Hat's UBI-based images, or build your own following Week 4's rules.

7Getting access

This course uses either the free Red Hat Developer Sandbox or an instructor-provided cluster.

The Developer Sandbox

  • Sign in with a Red Hat account. You get a time-limited, shared cluster with resource quotas.
  • You can't create projects. You're given one ready-made project, named after your user name (such as yourname-dev). Use it for everything.
  • To use oc, open the web console, choose your user name in the top-right corner, then Copy login command. It gives you an oc login --token=… --server=… command to paste into your terminal.

Installing oc

Download oc for your operating system from the web console's help menu (the question mark icon), under Command Line Tools. The download also includes kubectl. Put both somewhere on your PATH and check:

$ oc version --client
$ oc login --token=sha256~… --server=https://api.….openshiftapps.com:6443
$ oc whoami
$ oc project
Treat the token like a password

Anyone with your login token can act as you on the cluster until it expires. Don't paste it into shared documents, chat or screenshots.

8From Podman to OpenShift

Moving an application you built with Podman onto OpenShift takes three steps:

  1. Make the image reachable. The cluster can't see localhost/myapp on your workstation. Push the image to a registry the cluster can pull from, such as Quay (Week 3).
  2. Make sure it runs as any user. Non-root, group 0 permissions, a port above 1024 (Week 4).
  3. Describe it to the cluster, either with commands or with YAML:
$ podman push quay.io/student/myapp:1.0
$ oc create deployment myapp --image=quay.io/student/myapp:1.0 --port=8080
$ oc expose deployment myapp
$ oc expose service myapp
$ oc get route myapp

Or start from podman kube generate YAML and apply it with oc apply -f pod.yaml. A bare pod is a good test, but for anything real, wrap it in a deployment so the cluster keeps it running.

If your Quay repository is private, the cluster needs credentials too: a pull secret, which you'll create in Week 11.
