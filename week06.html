Week 6

When containers misbehave

Every container problem leaves evidence: an exit code, a log line, a setting in inspect, a port that answers on one side and not the other. This week gives you a method for collecting that evidence quickly, plus eight broken containers to practice on.

1Goals

By the end of this week you should be able to:

  • Follow a consistent sequence of checks instead of guessing.
  • Translate common exit codes into likely causes.
  • Use logs, events, inspect, top and stats to see what a container is doing and how it is configured.
  • Tell apart port-mapping, bind-address and DNS problems by testing from inside and outside the container.
  • Debug containers built from minimal images that lack shells and tools.
  • Expose a debugger port from a container safely during development.

2A troubleshooting method

Experienced administrators don't start by changing things. They follow the same order every time, because each step narrows the problem and some evidence disappears once you act.

  1. Observe the state. podman ps -a: is the container running, exited, restarting or never created? If it exited, with what code and how long after starting?
  2. Read the logs. podman logs NAME works even for exited containers. Most failures announce themselves here.
  3. Check the configuration. podman inspect NAME shows the actual command, environment, user, mounts, network and ports, not what you meant to type.
  4. Test from both sides. If a service doesn't answer, try it from inside the container with podman exec, then from the host. Where it stops working tells you which layer is broken.
  5. Change one thing at a time, recreate the container and check again. Changing three settings at once leaves you not knowing which one mattered.

Keep the failed container until you understand it. If you started it with --rm, its logs vanished with it, so rerun without --rm while debugging.

3Reading exit codes

When a container's main process ends, its exit code is the first clue. Codes from 0 to 124 come from the application itself, and their meaning is up to the app. Codes 125 to 127 come from Podman and the OCI runtime. Codes above 128 mean the process was ended by a signal: subtract 128 to get the signal number.

Common container exit codes
CodeMeaningTypical cause
0Finished successfullyA one-off command completed, or a shell with no input exited at once.
1General application errorMissing configuration, failed database connection. Read the logs.
125Podman itself failedBad option, name already in use, port already taken.
126Command can't be executedFile isn't executable, or permission denied on it.
127Command not foundTypo in CMD or ENTRYPOINT, or the program isn't installed in the image.
137Killed by SIGKILL (9)Out of memory, podman kill, or podman stop timed out.
139Segmentation fault (11)The program crashed, often a binary built for the wrong platform or library.
143Ended by SIGTERM (15)A normal podman stop of an app that doesn't trap the signal.
 
$ podman inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' NAME

For 137, check .State.OOMKilled. True means the memory limit killed it; false means something sent the signal.

4Logs and events

Podman captures standard output and standard error of the main process. On RHEL, rootless containers log to the systemd journal by default, so the logs survive until you remove the container.

$ podman logs --tail 50 web
$ podman logs -t --since 10m web      # with timestamps, last 10 minutes
$ podman logs -f web                  # follow live; Ctrl+C to stop

If an app writes to a log file inside the container instead of standard output, podman logs shows nothing useful. Read the file with podman exec web cat /path/to/log, or copy it out with podman cp.

Events

podman events records what happened to containers: created, started, died, removed, health status changes. It answers questions logs can't, such as "did this container restart three times overnight?"

$ podman events --since 1h --filter container=web
2026-10-08 09:41:02 container start 8d2f6c1e9b0a (image=…/httpd-24:latest, name=web)
2026-10-08 09:52:17 container died 8d2f6c1e9b0a (image=…/httpd-24:latest, name=web, containerExitCode=137)

5Looking at a live container

For a container that's running but behaving oddly, a few commands show what's going on without changing anything:

  • podman top web lists the processes inside, with the user each runs as. Useful to confirm the app is actually running and as which UID.
  • podman stats --no-stream shows CPU, memory, network and disk use per container. A memory figure creeping toward the limit predicts an OOM kill.
  • podman inspect web shows configuration. Narrow it with --format: {{.Config.Cmd}}, {{.Config.Env}}, {{.Config.User}}, {{.Mounts}}, {{.NetworkSettings.Networks}}.
  • podman exec -it web /bin/bash lets you look around: read config files, check environment variables, test connections.

Health checks

A container can be running without being healthy. Podman can run a check command on a schedule and record the result, which shows up in podman ps:

$ podman run -d --name web -p 8080:8080 \
    --health-cmd 'curl -fs http://localhost:8080/ || exit 1' --health-interval 30s \
    registry.access.redhat.com/ubi9/httpd-24
$ podman healthcheck run web   # run the check now; exit 0 means healthy

OpenShift takes this idea much further with readiness and liveness probes, which you'll configure in Week 14.

6Network checks

"I can't reach it" is the most common complaint, and it has several distinct causes. Test in this order:

  1. Inside the container: podman exec web curl -s localhost:8080. If this fails, the app isn't listening, or is listening on a different port. Check the logs.
  2. The mapping: podman port web. Is the host port mapped to the port the app actually uses? -p 8080:80 sends traffic to port 80, where nothing is listening.
  3. From the host: curl localhost:8080. If it works inside but resets from the host, the app is probably listening only on 127.0.0.1 inside its own network namespace. Configure it to listen on 0.0.0.0.
  4. From another container: names resolve only on user-defined networks (Week 2). Check podman inspect --format '{{.NetworkSettings.Networks}}' for both containers.
  5. From another machine: the host firewall must allow the port, for example sudo firewall-cmd --add-port=8080/tcp.
Exam habit

"Works inside, not outside" points to the port mapping or the bind address. "Fails inside too" points to the application. Decide which before changing anything.

7When the image has no tools

Good production images are minimal, which means curl, ps and sometimes even a shell are missing. You still have options:

  • Borrow a namespace. Start a toolbox container that joins the broken container's network: podman run -it --rm --network container:web registry.access.redhat.com/ubi9/ubi bash. Inside, localhost is the broken container's localhost.
  • Copy files out. podman cp web:/etc/app/config.yaml . needs nothing inside the container.
  • Explore the image, not the container. podman run -it --rm --entrypoint /bin/sh IMAGE skips the failing app so you can look at the files it would have used.
  • Keep a crashing container alive. podman run -d --name dbg --entrypoint sleep IMAGE infinity, then podman exec in and start the app by hand to watch it fail.
  • Mount the filesystem. podman unshare podman mount web prints a host path where you can browse the container's files with host tools.

8Remote debugging

Sometimes logs aren't enough and you want to step through code. Most language runtimes can open a debugger port that an IDE attaches to over the network. Inside a container that works the same way, with one extra step: publish the debugger port.

# Node.js: start the app with the inspector listening on all interfaces
$ podman run -d --name api -p 3000:3000 -p 9229:9229 \
    myapi:dev node --inspect=0.0.0.0:9229 server.js
# Python: the debugpy module listens for an IDE on port 5678
$ podman run -d --name api -p 8000:8000 -p 5678:5678 \
    myapi:dev python3 -m debugpy --listen 0.0.0.0:5678 app.py

Point your IDE's "attach to remote" configuration at localhost and the debugger port, and map the container's source path to your local source folder so breakpoints line up. A bind mount of your source directory makes the edit and debug loop fast.

Development only

A debugger port allows anyone who can reach it to run code inside your app. Never publish one on a shared or production host, and build production images without debugger tooling.

10Beyond Red Hat

Troubleshooting elsewhere

Docker

docker logs, inspect, stats, events, top and exec behave like their Podman twins, and the exit codes mean the same things. Docker Desktop adds a docker debug command that opens a toolbox shell in any container, even a minimal one. A popular community image, docker.io/nicolaka/netshoot, packs dozens of network tools for the "borrow a namespace" technique.

Kubernetes preview

The method from section 2 carries over directly; only the commands change:

Podman troubleshooting commands and their Kubernetes equivalents

Observability at scale

With hundreds of containers you can't read logs one at a time. Production platforms collect metrics with Prometheus and chart them in Grafana, gather logs centrally with tools such as Loki, Elasticsearch or OpenSearch, and trace requests across services with OpenTelemetry. OpenShift ships with a Prometheus-based monitoring stack built in.

Before you start

Watch for these during the lab

  • Troubleshooting labs usually hand you something broken on purpose. Gather evidence first (state, logs, inspect) before you change anything.
  • Fix the cause the lab is testing, not just the symptom. Recreating a container that will fail the same way doesn't count.
  • After fixing, verify the way a user would: from the host, with the published port.
  • Remote debugging steps may require a specific IDE or port. Follow the lab's values exactly.
