2Persistent volumes and claims

Week 5 split application code (in the image) from state (outside the container). Kubernetes does the same, but a pod can land on any node, so storage must be able to follow it. Kubernetes separates asking for storage from providing it:

  • A PersistentVolumeClaim (PVC) is a request made in your project: "I need 1 GiB, read-write, from this class of storage." Developers create these.
  • A PersistentVolume (PV) is a real piece of storage in the cluster: a cloud disk, an NFS export, a Ceph volume. It's cluster-scoped and usually created automatically.
  • A StorageClass names a kind of storage and the provisioner that creates PVs for it. When a PVC names a class (or the cluster default), the provisioner creates a matching PV and binds it to the claim. That's dynamic provisioning.
Access modes
ModeMeaningTypical storage
ReadWriteOnce (RWO)Mounted read-write by pods on one node at a time.Block storage: cloud disks, LVM, Ceph RBD
ReadWriteMany (RWX)Mounted read-write by pods on many nodes at once.File storage: NFS, CephFS, cloud file services
ReadOnlyMany (ROX)Mounted read-only by many nodes.Shared reference data
ReadWriteOncePodExactly one pod, anywhere.Strict single-writer databases

The storage class decides which modes are possible. Asking an RWO-only class for RWX leaves the PVC Pending forever. A class's reclaim policy decides what happens to the data when you delete the PVC: Delete (gone) or Retain (kept for an administrator to recover).

$ oc get storageclass
$ oc get pvc
NAME          STATUS   VOLUME          CAPACITY   ACCESS MODES   STORAGECLASS   AGE
web-content   Bound    pvc-3f9c…       1Gi        RWO            lvms-vg1       2m

3Using storage in a deployment

oc set volumes creates the claim (if needed) and mounts it in the pod template in one step. Because it changes the template, the deployment rolls out new pods:

$ oc set volumes deployment/web --add --name=content \
    --type=pvc --claim-name=web-content --claim-size=1Gi \
    --mount-path=/var/www/html
$ oc set volumes deployment/web     # list current volumes

The same thing in YAML: a volume in the pod spec refers to the claim, and a volume mount places it in the container.

    spec:
      volumes:
      - name: content
        persistentVolumeClaim:
          claimName: web-content
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/httpd-24:1-338
        volumeMounts:
        - name: content
          mountPath: /var/www/html
RWO and many replicas

With an RWO volume, pods scheduled on a different node from the one holding the volume get stuck in ContainerCreating with a "Multi-Attach" error. Scale a deployment that shares a volume only with RWX storage, or give each replica its own volume with a StatefulSet.

The random UID from Week 12 owns nothing in a new volume, but OpenShift sets the volume's group ownership (fsGroup) to the project's group, so the container can still write. That's one more reason images should rely on group permissions.

4ConfigMaps and Secrets

The same image should run in development, test and production; only its configuration changes. Kubernetes stores configuration in two kinds of object:

  • ConfigMap: non-sensitive settings such as feature flags, URLs and whole configuration files.
  • Secret: passwords, tokens, keys and certificates. Values are base64-encoded, which is not encryption; what protects them is RBAC (the view role can't read secrets) and, if the administrator enables it, encryption in etcd.
$ oc create configmap web-config --from-literal=GREETING=hello --from-file=app.conf
$ oc create secret generic db-creds --from-literal=password=s3cret

Two ways to use them

  • As environment variables, with oc set env deployment/web --from=configmap/web-config. Simple, but values are fixed when the container starts; change the ConfigMap and you must restart the pods.
  • As files, with oc set volumes deployment/web --add --type=configmap --configmap-name=web-config --mount-path=/etc/web. Each key becomes a file. Mounted files update in running pods after a short delay, although the app has to notice.
Don't leak secrets

Never put real secrets in YAML files committed to Git, and remember that oc get secret NAME -o yaml shows them base64-encoded to anyone with access. Environment variables can appear in crash reports and logs; mounted files are often safer for sensitive values.

5Health probes

Kubernetes knows a container is running. Probes tell it whether the application is actually working. The kubelet runs each probe on a schedule:

Probe types
ProbeQuestionWhen it fails
StartupHas the app finished starting?Other probes wait. After the threshold, the container is restarted.
ReadinessCan it take traffic right now?The pod is removed from service endpoints. Not restarted.
LivenessIs it still healthy, or stuck?The container is restarted.

A probe checks with an HTTP GET (any 2xx or 3xx status passes), a TCP connection, or a command run in the container. Timing settings: initialDelaySeconds, periodSeconds (default 10), timeoutSeconds and failureThreshold (default 3 failures in a row).

$ oc set probe deployment/web --readiness --get-url=http://:8080/ --period-seconds=5
$ oc set probe deployment/web --liveness --get-url=http://:8080/ --initial-delay-seconds=15
$ oc set probe deployment/web --startup --get-url=http://:8080/ --failure-threshold=30 --period-seconds=2
Common mistakes

A liveness probe that runs before a slow app has started kills it over and over; add a startup probe instead of a huge initial delay. A probe on the wrong port or a path that returns 404 fails forever. And a liveness probe that checks a database makes every pod restart when the database blips; liveness should test only the container itself.

7Requests and limits

Each container can declare two numbers for CPU and for memory:

  • Requests are what the container needs. The scheduler places a pod only on a node with that much unreserved capacity. If no node has room, the pod stays Pending with an "Insufficient cpu" event.
  • Limits are the most it may use. Over the CPU limit, the container is throttled (slowed down). Over the memory limit, it's killed: OOMKilled, exit code 137, exactly as with Podman in Week 6.

CPU is measured in cores or millicores (500m is half a core); memory in bytes with suffixes (128Mi, 1Gi).

$ oc set resources deployment/web --requests=cpu=100m,memory=128Mi --limits=cpu=500m,memory=256Mi
$ oc adm top pods

Requests and limits also decide a pod's quality of service: Guaranteed (requests equal limits), Burstable (requests lower than limits) or BestEffort (neither set). When a node runs short of memory, BestEffort pods are evicted first. Administrators enforce sensible values per project with a LimitRange (defaults and maximums per container) and a ResourceQuota (totals for the whole project).

8Autoscaling

A HorizontalPodAutoscaler (HPA) changes a deployment's replica count to keep average CPU use near a target, expressed as a percentage of the request. That's why autoscaling needs a CPU request; without one, the HPA shows <unknown> and does nothing.

The rule it applies is simple: desiredReplicas = ceil(currentReplicas × currentUtilization ÷ targetUtilization), kept between the minimum and maximum. It scales up quickly, and scales down only after load has stayed low for a while (five minutes by default), so a short lull doesn't remove capacity.

$ oc autoscale deployment/web --min=2 --max=8 --cpu-percent=60
$ oc get hpa
NAME   REFERENCE        TARGETS        MINPODS   MAXPODS   REPLICAS   AGE
web    Deployment/web   cpu: 34%/60%   2         8         2          5m

    10Beyond Red Hat

    Storage, secrets and scaling elsewhere

    • Storage classes differ by platform: gp3 EBS volumes on AWS, Azure Disk and Azure Files, Google Persistent Disk and Filestore. On bare metal, Rook-Ceph, Longhorn and NFS provisioners are common; OpenShift Data Foundation is Red Hat's Ceph-based option. PVCs and access modes are the same everywhere.
    • Secrets management. HashiCorp Vault and cloud secret managers often hold the real values, synced into Kubernetes secrets by the External Secrets Operator. Sealed Secrets lets you commit encrypted secrets safely to Git.
    • More autoscalers. The Vertical Pod Autoscaler adjusts requests rather than replica counts. KEDA scales on events such as queue length, down to zero. The Cluster Autoscaler and Karpenter add or remove nodes when pods can't be scheduled.
    • Probes, requests and limits are core Kubernetes, identical on every platform, and the same in Docker Compose's healthcheck and deploy.resources keys on a smaller scale.
