Containers on your own computer

This course runs on Red Hat tools in a managed lab. This page is for your own laptop: install a container engine on Windows or Mac, then use it for real things, spinning up a database in seconds, trying a language without installing it, running a home lab, or practicing security in disposable, isolated environments. It's optional, ungraded, and genuinely useful.

1Why do this

Enrichment, not assessed

The same skills you're learning for the EX188 exam are, slightly rephrased, some of the most useful everyday tools in computing. On your own machine, a container engine lets you:

  • Run anything without installing it. Try PostgreSQL, Redis, a specific Python version, or a whole web stack, then delete it without a trace. No "I installed five databases and now my laptop is a mess."
  • Keep projects isolated. Each project gets exactly the versions it needs, with no conflicts between them.
  • Reproduce environments exactly. The container that works on your laptop works on your teammate's, and on the server.
  • Experiment safely. Especially for security work: run suspect tools, vulnerable apps and scanners in a throwaway sandbox instead of on your real system.

None of this is required for the course. It's here because once you can do it, you'll reach for it constantly.

2Docker or Podman?

Two good choices run on Windows and Mac. Both run the same OCI images and use nearly the same commands as the Podman you're learning. Pick one; you can always try the other later.

Docker Desktop

  • The most widely used option, so almost every tutorial, Stack Overflow answer and security-tool README assumes it.
  • Smooth installer for Windows and Mac, with a built-in dashboard, Kubernetes toggle and Dev Containers support.
  • Free for students: the Docker Personal plan covers personal use, education and small businesses. A paid plan is only needed for commercial use in larger organizations.
  • One catch: anonymous pulls from Docker Hub are rate-limited, so sign in with a free Docker account to avoid "429 Too Many Requests" errors.

Podman Desktop

  • Free and open source with no licensing conditions at all, whatever you use it for.
  • It's the same tool family you use in this course, so your podman skills transfer one-to-one, which also helps for EX188.
  • Runs rootless and daemonless by design, the security model this course emphasizes.
  • Reach for it if a school or work laptop makes Docker Desktop's licence or admin requirements awkward, or if you simply prefer open source.

Everything on the rest of this page works with either. Where a command differs, both are shown. If you installed Podman Desktop, you can usually just replace docker with podman.

3Installing

Choose your operating system.

Containers need a Linux kernel, so on Windows the engine runs inside WSL 2 (the Windows Subsystem for Linux). The installer sets most of this up, but two things must be enabled first, and they're the usual cause of a failed install:

  1. Turn on virtualization. Open Task Manager, Performance, CPU, and check that "Virtualization: Enabled" appears. If not, enable it in your PC's BIOS/UEFI (often called "Intel VT-x", "AMD-V" or "SVM").
  2. Install WSL 2. In PowerShell as administrator, run wsl --install, then restart. This also installs a Linux distribution you can use.
  3. Install the engine.
    • Docker: download Docker Desktop for Windows from docker.com, run the installer, and keep "Use WSL 2 instead of Hyper-V" checked.
    • Podman: download Podman Desktop from podman-desktop.io; it will offer to set up the Podman machine (a small Linux VM) on first run.

Open a new terminal (PowerShell, Windows Terminal, or your WSL distro) and continue to the first commands below.

If install fails

Nearly always it's virtualization turned off in the BIOS, or WSL 2 not installed or not set as default (wsl --set-default-version 2). On some managed or school laptops, virtualization is locked off and you may not be able to change it; use the lab environment there instead.

On a Mac the engine runs inside a lightweight Linux virtual machine the installer manages for you. There's no BIOS step.

  1. Know your chip. Apple menu, About This Mac. "Apple M1/M2/M3/M4" is Apple Silicon (ARM); "Intel" is the older architecture. Download the matching build.
  2. Install the engine.
    • Docker: download Docker Desktop for Mac (Apple Silicon or Intel) from docker.com, open the .dmg, and drag Docker to Applications.
    • Podman: install Podman Desktop from podman-desktop.io, or with Homebrew: brew install podman podman-desktop, then podman machine init && podman machine start.
Apple Silicon and x86 images

Apple Silicon Macs run ARM images natively and fast. Some images are built only for Intel (x86-64); those run through emulation, which is slower and occasionally breaks. If an image fails to start or crashes oddly, try docker run --platform linux/amd64 … (same flag for podman). Prefer images that list an arm64 build when you have the choice.

On Linux there's no VM; containers run directly on your own kernel, which is faster and lighter. You likely already have Podman from this course.

  • Fedora, RHEL, CentOS Stream:sudo dnf install podman (often preinstalled). For Docker, follow Docker's instructions to add its repository and install docker-ce.
  • Ubuntu, Debian:sudo apt install podman, or install Docker Engine from Docker's official repository.
  • Podman Desktop and Docker Desktop both have Linux builds if you want the graphical dashboard, but the command line alone is enough.

With Docker on Linux, adding yourself to the docker group lets you skip sudo, but remember from Week 2 that this is effectively granting root. Podman runs rootless without any of that.

4Your first commands

Confirm it works. These are exactly the commands from Week 2, with docker in place of podman:

$ docker version
$ docker run --rm docker.io/library/hello-world
$ docker run -d --name web -p 8080:80 docker.io/library/nginx
# open http://localhost:8080 in your browser
$ docker ps
$ docker logs web
$ docker stop web && docker rm web

With Podman Desktop, replace docker with podman. Note nginx here listens on port 80 inside the container, because Docker's default images often assume root; that's one of the differences from Red Hat's images you learned about in Week 4.

5For programming

A few recipes that pay off immediately. Copy, run, and delete when you're done.

A database in ten secondsCS

You need PostgreSQL for a class project but don't want to install and configure it. Run it in a container, use it, then throw it away.

$ docker run -d --name pg -e POSTGRES_PASSWORD=dev -p 5432:5432 docker.io/library/postgres:16
# connect from your app at localhost:5432, user postgres, password dev
$ docker exec -it pg psql -U postgres
# when finished:
$ docker rm -f pg

Swap postgres:16 for mysql:8, mariadb:11, redis:7 or mongo:7 for other databases. Add a volume (Week 5) if you want the data to survive: -v pgdata:/var/lib/postgresql/data.

Try a language without installing itCS

You want to test something in a specific Python, Node or Go version without changing what's on your machine.

$ docker run -it --rm docker.io/library/python:3.12 python
$ docker run -it --rm -v "$PWD":/app -w /app docker.io/library/node:20 npm test
$ docker run -it --rm -v "$PWD":/app -w /app docker.io/library/golang:1.22 go run main.go

The -v "$PWD":/app mounts your current folder into the container (a bind mount, Week 5), and -w /app runs the command there, so the container works on your real files. On Windows PowerShell use ${PWD}.

A reproducible dev environment in VS CodeCS

You want everyone on a project, including future-you on a new laptop, to get the exact same tools automatically.

Install the Dev Containers extension in VS Code. Add a .devcontainer/devcontainer.json to your project naming a base image and the tools you need. Then "Reopen in Container" builds it and drops you into a shell with everything installed. The config lives in Git, so the environment travels with the code.

// .devcontainer/devcontainer.json
{
  "image": "mcr.microsoft.com/devcontainers/python:3.12",
  "forwardPorts": [8000],
  "postCreateCommand": "pip install -r requirements.txt"
}

Dev Containers use Docker by default and also work with Podman. This is the idea behind GitHub Codespaces, which runs the same dev container in the cloud.

A Jupyter notebook for data workCS

You want to explore data in Python with pandas, NumPy and matplotlib, without installing a scientific stack on your laptop.

$ docker run --rm -p 8888:8888 -v "$PWD":/home/jovyan/work docker.io/jupyter/scipy-notebook
# copy the http://127.0.0.1:8888/?token=… URL it prints into your browser

Your notebooks are saved in the mounted folder, so they survive after you stop the container. The whole data-science toolkit comes preinstalled.

Run a one-off tool without installing itCS

You need to convert a file, resize images or run a formatter once, and don’t want that tool cluttering your system.

# Convert and resize images with ImageMagick
$ docker run --rm -v "$PWD":/work -w /work docker.io/dpokidov/imagemagick *.png -resize 50% out.png
# Pretty-print and query JSON with jq
$ cat data.json | docker run --rm -i docker.io/stedolan/jq '.items | length'

This is a clean way to use command-line tools you need rarely: pull, run, and the tool leaves nothing behind.

Preview a website or documentation locallyCS

You’re building a static site, a portfolio or project docs and want to see them exactly as they’ll be served, without installing a web server.

$ docker run --rm -p 8080:80 -v "$PWD":/usr/share/nginx/html:ro docker.io/library/nginx
# open http://localhost:8080 ; your files are served read-only

Swap nginx for a documentation image such as squidfunk/mkdocs-material to live-preview Markdown docs as you edit them.

A whole stack with ComposeCS

Your app needs a web server, a database and a cache together. Describe them once and start them with one command (Week 7).

# compose.yaml
services:
  web:
    build: .
    ports: ["8000:8000"]
    depends_on: [db]
  db:
    image: docker.io/library/postgres:16
    environment:
      POSTGRES_PASSWORD: dev
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata: {}
$ docker compose up -d     # podman-compose up -d with Podman
$ docker compose down

6For cybersecurity

Containers are a natural fit for security work: a disposable, isolated environment you can break, infect or attack and then delete. A few starting points. Keep reading the safety section afterward, because some of this needs care.

A Kali Linux toolboxSecurity

You want the standard penetration-testing tools without dual-booting or dedicating a VM.

$ docker run -it --rm docker.io/kalilinux/kali-rolling
# inside, install what you need:
$ apt update && apt install -y nmap nikto

For the full tool set, Kali publishes themed metapackages (kali-linux-headless, and others). The container starts clean each time with --rm; use a volume or a custom image if you want your tools to persist.

A deliberately vulnerable target to practice onSecurity

You need something to scan and exploit, legally and safely. Several projects exist exactly for this, designed to run in a container on your own machine.

# OWASP Juice Shop: a modern vulnerable web app
$ docker run -d --name juice -p 3000:3000 docker.io/bkimminich/juice-shop
# open http://localhost:3000 and work through the challenges

# DVWA: the classic Damn Vulnerable Web Application
$ docker run -d --name dvwa -p 8080:80 docker.io/vulnerables/web-dvwa

Scan your target from the Kali container, or from a scanner image, and compare results. Because everything is local and disposable, you can attack freely and reset by deleting the containers.

Run security scannersSecurity

You want to use professional tools without installing them, or to scan container images themselves (which connects straight back to Week 3).

# Scan a web app with OWASP ZAP
$ docker run --rm -t docker.io/zaproxy/zap-stable zap-baseline.py -t http://YOUR-TARGET:3000

# Scan a container image for known vulnerabilities with Trivy (Week 3)
$ docker run --rm docker.io/aquasec/trivy image docker.io/library/nginx:latest

Image scanning is part of the container supply-chain practices from Week 3. Running a scanner in your build pipeline, and blocking images with critical findings, is a real job skill.

Analyze something suspicious in isolationSecurity

You've been handed a file or a URL and you want to poke at it without risking your own system.

A container gives you a throwaway, network-limited space. Start one with no network at all (--network none) when you only need to inspect a file, add a read-only root filesystem (--read-only), and never mount your real home directory into it. Understand the limits, though: a container shares the host kernel (Week 1), so it is not a security boundary strong enough for genuinely dangerous malware. For that, use a full virtual machine, or a dedicated malware-analysis sandbox, on hardware you're willing to wipe.

$ docker run -it --rm --network none --read-only \
    -v "$PWD/sample":/data:ro docker.io/library/ubuntu bash

Capture and inspect network trafficSecurity

You want to see what an application is actually sending on the wire, or practice reading packet captures.

# A toolbox packed with network utilities (tcpdump, dig, curl, nmap, and more)
$ docker run -it --rm docker.io/nicolaka/netshoot
# Capture packets to a file you can open in Wireshark later
$ docker run --rm -v "$PWD":/cap docker.io/nicolaka/netshoot tcpdump -i any -w /cap/capture.pcap

The netshoot image is a security and networking staple: when a container has no tools of its own, you attach this one to its network (the Week 6 trick) and debug from inside.

Intercept web traffic with a proxySecurity

A core web-security skill is watching and modifying the requests a browser or app makes. mitmproxy does this and runs happily in a container.

$ docker run --rm -it -p 8080:8080 docker.io/mitmproxy/mitmproxy
# point your browser or app at the proxy on localhost:8080, then watch the requests

Use it against your own apps or the deliberately vulnerable targets above. It’s the open-source cousin of the intercepting proxies used in professional web testing.

More practice targets: WebGoat and beyondSecurity

Once Juice Shop and DVWA feel familiar, you want more, and more varied, legal practice.

# OWASP WebGoat: a guided, lesson-based vulnerable app
$ docker run -d --name webgoat -p 8080:8080 -p 9090:9090 docker.io/webgoat/webgoat

Many classic challenges ship as containers or Compose files: look for OWASP projects, the Juice Shop “multi-juicer” for group play, and vulnerable-by-design VMs that have been packaged as images. Because each one is isolated and disposable, you can run several at once and reset instantly.

A pocket crypto and forensics workbenchSecurity

You’re working a capture-the-flag challenge or analysing a file and need encoders, decoders, hashing and data tools in one place.

# CyberChef: “the cyber Swiss Army knife”, in your browser, fully offline
$ docker run --rm -d --name cyberchef -p 8000:80 docker.io/mpepping/cyberchef
# open http://localhost:8000 ; everything runs locally, nothing leaves your machine

Running CyberChef locally in a container means you can decode and analyse sensitive data without sending it to a website. It pairs well with a Kali container for CTF and forensics practice.

A home lab you can rebuild in minutesSecurity

You want to practice logging, monitoring and defense, not just attacks.

Many blue-team and home-lab tools ship as containers or Compose files: log stacks (Elasticsearch, Kibana and friends), network monitors, honeypots, vulnerability managers and self-hosted services. Running them in containers means you can stand up a realistic environment, experiment, and tear it all down with one compose down. It's the fastest way to build the kind of hands-on home lab that employers and certifications value.

7Staying safe and tidy

A few habits keep container experiments from becoming problems, and matter even more for security work.

  • A container is not a strong security boundary. It shares the host kernel (Week 1). It's great for isolating ordinary software and dev environments. For truly hostile code, use a full VM or a purpose-built sandbox on disposable hardware.
  • Only attack what you're allowed to. Practice against the deliberately vulnerable apps above, or systems you own, or an authorized lab. Scanning or attacking anything else, including your school or employer's network, can be a crime. When in doubt, don't.
  • Trust your images. Pull from official or well-known publishers, prefer images with a clear source, and be wary of random images that promise hacking tools, which are a classic way to deliver malware. Scan images you're unsure about (recipe above).
  • Limit what a risky container can touch.--network none or a dedicated network, --read-only, a memory limit (--memory 512m), and never bind-mount your whole home directory.
  • Prefer rootless. Podman is rootless by default; Docker has a rootless mode. Either reduces the damage an escape could do.
  • Clean up. Images and volumes pile up fast. docker system df shows usage; docker container prune, docker image prune -a and docker volume prune reclaim space. (Same commands with podman.)

8Where to go next

If you enjoy this, natural next steps:

  • Run Kubernetes locally. Docker Desktop and Podman Desktop both have a one-click Kubernetes option, and kind or minikube give you a small cluster to practice the second half of this course on your own machine.
  • Build and publish your own images (Weeks 3 and 4) to a free registry such as Docker Hub, GitHub Container Registry or Quay.
  • Set up CI. GitHub Actions can build and test your project in containers on every push, for free on public repositories.
  • For security students: work through the challenges in Juice Shop or DVWA, try a capture-the-flag platform, and build out a home lab. These are exactly the hands-on experiences that strengthen a cybersecurity resume.

And of course, everything you practice here reinforces the course and the EX188 certification. Containers you run for fun are still containers you understand for the exam.
